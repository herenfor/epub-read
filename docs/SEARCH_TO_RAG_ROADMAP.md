# 从正文搜索到 RAG 的开发方向

## 文档状态

- 性质：长期能力路线与后续分支的范围基线。
- 当前状态：已完成技术调研、B-059/C-48 当前书搜索和 C-53 地基；C-54/C-56 已完成跨书 SQLite FTS5、书架/阅读器共享运行时、真实 Worker、可配置设备并发、单写入和阅读优先的通用语料流水线，并随 `0.1.9-beta.2` 通过 Windows 基础全文搜索验收。RAG C-57 已完成模型文件资产层代码，等待 Windows 发布版验收；真实模型运行时、Embedding、向量检索、标签和 RAG 仍未实现，也不代表稳定发布能力。
- 当前阶段：**RAG C-57 模型资产管理代码及 Windows Tauri dev 核心链路已通过；C-57.6 发行门禁代码与本地矩阵完成，等待 Windows 双包验收，然后进入 C-58-Prep**。`0.1.9-beta.2` 的 Windows 基础全文搜索已验收；第一阶段结构化语料和第二阶段核心建库/查询/跳转完成。C-57 只完成模型包/下载/ownership 基础设施，尚未接入真实模型运行时或第四阶段语义索引。
- 当前平台重点：先研究 Windows 桌面端；Android 只保留未来扩展方向。
- 阶段实现目标：跨书全文检索、语义检索、相似内容、建议标签和智能分类。
- 最终目标：在可靠检索与原文锚点之上，实现带引用的 AI 问答和分层正文总结。
- 当前分支定位：RAG 作为同一 EPUB Reader 仓库和同一 Tauri 应用中的可选能力模块开发，不拆成第二个产品；首个里程碑只建立模块、数据和生命周期地基，不接入真实模型。

本文所说的 RAG 不是单一“聊天模型功能”。搜索、语义向量、分类、生成分别是可替换的层；没有生成模型时，全文检索、语义搜索和固定体系标签仍应独立可用。

## 总体边界

```text
EPUB 源文件
  → 结构化正文语料
  → 稳定章节/文本锚点
  ├─ SQLite FTS → 全文搜索
  ├─ EmbeddingProvider → 语义向量
  ├─ VectorStore/Retriever → 相似内容与跨书检索
  ├─ TaggingService → 建议标签与智能分类
  └─ GeneratorProvider → RAG 问答与正文总结（最终阶段）
```

必须保持以下边界：

- 阅读器核心不能依赖生成模型才能打开、搜索或阅读书籍。
- 索引和向量属于可删除、可重建的本机缓存，不进入阅读进度存档。
- 用户标签、用户确认的 AI 标签和用户编辑过的摘要属于可同步数据。
- 嵌入模型与生成模型分别配置；更换生成模型不得触发全库向量重建。
- 模型供应商可替换，不绑定 OpenAI、Ollama 或单一下载平台。
- AI 结果必须能回溯到书名、章节、正文块和稳定锚点。

### 2026-08-24 默认运行路线修订：GPU 优先

此前路线把 Ollama 与项目内运行时并列得过于靠前。现确定：**普通用户的默认本地 AI 路径不依赖 Ollama，也不要求另装或维护第三方模型服务**。Ollama 默认占用其自身数据目录、模型管理和进程生命周期不归阅读器控制，因此只保留为未来高级兼容 Provider，不再作为 C-58 或默认生成能力的前置条件。

- C-58 不再以满负载 CPU 作为普通用户默认路径。先建立硬件/后端探测、资源准入、取消和故障隔离，再接入项目维护、版本固定的 Windows GPU-first Embedding Provider，消费 C-57 已安装且 verified 的默认嵌入模型资产。
- 后续生成能力优先采用项目构建、审计并固定版本的 llama.cpp sidecar；sidecar 与 GGUF 模型包分离，普通模型包不得携带 EXE/DLL。
- 普通用户默认使用项目推荐模型，不建设大型模型市场或复杂多模型选择 UI；加速模式统一为“自动推荐 / GPU 兼容 / NVIDIA CUDA / CPU 兼容”，只暴露经过支持矩阵验证的选项和资源提示。
- 高级用户替换模型时使用带 manifest/digest 的约定目录、C-57 linked 资产或未来受控能力插件；“直接替换文件”仍须经过格式、大小、SHA、维度/上下文和 Provider 兼容性校验，不能绕过资产层。
- Ollama、OpenAI-compatible、局域网和其他厂商服务后置为可选 HTTP Provider；未配置时不探测、不启动、不占用 C 盘，也不影响默认本地能力。
- Provider 运行组件由应用构建/审计和更新，模型资产由 C-57 管理；两者不得重新合并成可下载任意可执行代码的插件包。

四种模式采用以下后端：

| 用户选项 | Embedding | 生成 | 兼容范围与行为 |
|---|---|---|---|
| 自动推荐 | 已验收的 Windows 通用 GPU EP；具备兼容组件的 NVIDIA 可优先 CUDA | NVIDIA 优先 CUDA sidecar；其余已验收设备优先 Vulkan sidecar | 综合厂商、驱动、显存、模型格式和支持矩阵选择；GPU 失败不得静默切到高负载 CPU |
| GPU 兼容 | WinML/DirectML ONNX EP | llama.cpp Vulkan sidecar | 主要覆盖 AMD、Intel、无兼容 CUDA 组件的 NVIDIA，以及通过 DX12/Vulkan 探测和实测的其他显卡 |
| NVIDIA CUDA | ONNX Runtime CUDA EP | llama.cpp CUDA sidecar | 仅 NVIDIA；CUDA/cuDNN/驱动或受控运行组件不匹配时，提示改用 GPU 兼容模式 |
| CPU 兼容 | ONNX Runtime CPU EP | llama.cpp CPU sidecar，仅限满足资源门槛的模型 | 无可用 GPU、虚拟机或诊断场景；严格限制线程、批量、内存和后台优先级，并提示速度风险 |

厂商名称本身不是放行条件。NVIDIA 以 CUDA 为性能路径、WinML/DirectML 或 Vulkan 为兼容路径；AMD 首版使用 WinML/DirectML（Embedding）和 Vulkan（生成）；Intel 首版也走通用路径，OpenVINO/SYCL 仅在独立打包和真实硬件验收后加入自动推荐；其他显卡只有在 DX12/Vulkan 能力、驱动、显存预算与项目验收均满足时才启用通用路径。

能力探测不得加载模型。运行前必须执行显存/共享内存准入，阅读期间降低或暂停后台建库。GPU 初始化失败、显存不足或 sidecar 崩溃必须可以取消和释放；只有用户主动选择 CPU 兼容或明确确认一次性回退时才能使用 CPU 推理。

## 插件化与发行路径

RAG 与模型能力采用“可插拔能力模块”设计，方便启用、停用和发行不同版本；第一版不建设允许第三方任意加载 DLL、JS 或其他进程内代码的开放插件系统。开放动态代码会提前引入 ABI、权限、签名、崩溃隔离、安全和许可证风险，与当前实现目标不相称。

### 三层能力边界

1. **基础搜索核心**始终随阅读器提供：EPUB 正文提取、标准化、全文搜索、原文锚点、高亮和跳转。它不能依赖模型或插件，否则 AI 能力失效会破坏普通搜索。
2. **智能检索模块**可以启用或停用：`EmbeddingProvider`、向量存储、混合检索、相似内容、建议标签和智能书架。停用时不得加载嵌入模型或启动后台建库；已有索引由用户选择保留或删除，全文搜索继续可用。
3. **生成式 AI 模块**完全可选：`GeneratorProvider`、带引用 RAG 问答、章节摘要和全书总结。没有生成模块时，智能检索、相似内容和固定体系标签仍然可用。

### 能力插件与模型包分离

- 能力插件负责“怎样运行”：例如内置 ONNX、内置 llama.cpp sidecar、Ollama HTTP 或 OpenAI-compatible HTTP。
- 模型包负责“运行什么”：例如 ONNX 嵌入模型、GGUF 生成模型及其 tokenizer/config/manifest。
- 更换兼容模型是数据选择，不应安装新的代码插件。
- 模型包必须记录格式、用途、版本、digest、维度/上下文、设备建议、许可证和来源。

能力声明方向：

```json
{
  "id": "ollama",
  "version": "1",
  "capabilities": ["embedding", "generation"],
  "transport": "http"
}
```

```json
{
  "id": "builtin-onnx",
  "version": "1",
  "capabilities": ["embedding", "reranking"],
  "transport": "in-process"
}
```

Provider 实现顺序按“默认路径优先、高级兼容后置”调整：

```text
BuiltinOnnxProvider       → C-58B，GPU-first embedding；reranking 后续评估
BuiltinLlamaCppSidecar    → 默认 generation 候选，固定版本并由项目维护
OllamaProvider            → 后置高级兼容，embedding / generation
OpenAICompatibleProvider  → 后置高级兼容，按服务声明能力
```

内置 llama.cpp 优先以受控 sidecar 运行，使推理崩溃与阅读器主进程隔离；仅监听回环地址并使用临时端口和鉴权，或改用等价的受控 IPC。生成默认 GPU-first：NVIDIA 优先 CUDA，AMD/Intel/其他已验收设备优先 Vulkan，CPU 仅为受限兼容路径。各后端必须按项目支持矩阵独立构建、固定版本和验收，普通用户只选择四种稳定模式，不直接管理后端二进制。

### 发行形态

不同发行版可以共享一套代码和数据 schema，通过构建功能与打包内容决定能力，不复制业务实现：

| 发行形态 | 基础全文搜索 | 智能检索/分类 | 内置生成运行时 |
|---|---:|---:|---:|
| 基础版 | 是 | 否 | 否 |
| 智能检索版 | 是 | 是 | 否 |
| AI 完整版 | 是 | 是 | 是 |

基础版不依赖 Ollama。高级设置或受控能力插件未来可以显式连接 Ollama/兼容远程 Provider，但默认不展示为普通模型选择流程，也不得在启动时自动探测。运行时必须按 capability 判断功能，不得仅根据版本名称或某个模型文件是否存在推断。

**C-57.5 已建立首批发行隔离**：Core是默认正式构建，保留结构化语料、Worker、SQLite FTS和跨书全文搜索；编译期不包含模型资产面板、模型下载命令、Provider runtime入口及其 `reqwest/fs2` 依赖。AI是显式开发edition，前端使用 `VITE_EDITION=ai`，Rust使用`ai` feature，并以独立的Windows identifier和app-data运行，防止实验数据库或安装覆盖影响Core。两者来自同一代码树，基础版热修复必须回合并到AI开发线，禁止复制第二套长期源码。

当前`ai` feature只覆盖C-57模型资产和开发Provider面板，不代表已经实现Embedding、GPU、向量或生成。未来C-58A/C-58B和生成sidecar继续归入可选智能层；Core构建矩阵必须持续作为合入门槛。

**C-57.6 在 C-58 前收紧发行门禁**：Core/AI分别使用`dist/core`、`dist/ai`和独立Rust target；Cargo无参数安全默认为Core，AI只能显式启用；构建期metadata与桌面启动build-info共同拒绝前后端edition混装；AI面板CSS和开发探针不进入Core。`tsc`仍全量检查，因此紧急Core发行从稳定分支进行，同一修复再合并到AI开发线；C-57.6不以排除AI源码来伪造独立类型检查。

### 当前预留状态

- 当前书与跨书基础搜索结果均携带章节路径/标题、原文范围和稳定文本锚点；跨书结果还能关联书名/作者和内容指纹，可作为未来引用与检索的上游入口。
- `EmbeddingProvider`、`GeneratorProvider`、`RerankProvider`、capability manifest、注册表和惰性 runtime 已实现；当前仅注册开发 mock，不是模型运行时。
- Rust 已有独立 SQLite schema/迁移/清理、FTS 表、分批 staging、任务状态机和全库任务互斥；前端已有真实 Worker 建库执行器与共享运行时。仍没有向量存储、真实模型运行时或动态插件加载器。
- 现有 `tauri-plugin-*` 是编译期 Tauri 平台插件，与未来 AI 能力插件不是同一机制。

## 第四阶段：语义索引

- [ ] 批量生成正文块向量，模型只加载一次并使用批处理。
- [ ] 保存正文块、向量和模型身份的对应关系。
- [ ] 评估 Float32、Float16 与 Int8 的质量、速度和空间。
- [ ] 支持单本、增量和全库建库。
- [ ] 支持暂停、继续、取消、失败重试和应用重启恢复。
- [ ] 单本失败不得使整库事务失败。
- [ ] 阅读期间降低或暂停后台任务，限制线程、CPU和内存。
- [ ] 显示书籍级与全库级进度。
- [ ] 支持重新索引单本、全部重建和一键清理。
- [ ] 模型、模型 digest、维度或切块版本变化时只失效对应索引。
- [ ] 初期优先精确余弦检索；规模实测需要后再引入近似索引。
- [ ] 向量存储通过适配层接入，不能让持久格式永久绑定 pre-v1 扩展。

索引身份至少包含：

```text
bookFingerprint
parserVersion
normalizerVersion
chunkerVersion
embeddingProvider
embeddingModelId
embeddingModelDigest
dimensions
```

## 第五阶段：智能检索（主要实现目标）

- [ ] 当前书和跨书语义搜索。
- [ ] 自然语言描述搜索。
- [ ] 在模型支持时提供跨语言检索。
- [ ] 查找相似段落、相似章节和相似书籍。
- [ ] 从当前阅读位置寻找相关内容。
- [ ] 关键词检索与向量检索并行。
- [ ] 使用 RRF 或经评测确认的方式融合结果。
- [ ] 人名、术语和原句查询提高关键词权重。
- [ ] 描述性问题提高语义结果权重。
- [ ] 支持书籍、作者、标签和范围过滤。
- [ ] 显示相关度、召回方式、书名、章节和原文片段。
- [ ] 点击结果可靠跳转至原文锚点。
- [ ] 无嵌入模型或模型不可用时自动降级为全文搜索。
- [ ] 允许用户反馈相关/不相关，为离线评测保留数据边界。

## 第六阶段：标签与智能分类（主要实现目标）

### 用户标签

- [ ] 创建、重命名、删除、分组、着色和组合筛选。
- [ ] 一个书籍支持多个标签。
- [ ] 用户标签始终优先，AI不得静默覆盖。
- [ ] 用户标签和用户确认结果可进入同步存档。

### 固定标签体系

- [ ] 按场景、题材、风格、人物等维度建立标签体系。
- [ ] 每个标签保存名称、说明、父级、同义词和体系版本。
- [ ] 支持互斥、包含和共存规则。
- [ ] 标签说明可以生成向量并与书籍内容比较。

### 建议标签

- [ ] 先以规则、元数据和标签向量相似度生成候选。
- [ ] 输出置信度并区分书级与章节级标签。
- [ ] 每个建议保存证据正文块，点击可以回到原文。
- [ ] AI结果初始为 suggested，用户确认后才成为正式标签。
- [ ] 用户可以拒绝建议，拒绝结果不会反复出现。
- [ ] 重新计算不得覆盖用户确认、拒绝或手工修改。
- [ ] 生成式模型存在时可复核候选，但不作为基础分类的依赖。

### 智能书架与推荐

- [ ] 根据单个或多个标签建立动态书架。
- [ ] 根据内容向量生成相似作品和主题聚类。
- [ ] 根据用户选定的参考书寻找相似书籍。
- [ ] 展示推荐依据，允许关闭或删除智能规则。

## 第七阶段：检索质量与性能评测

- [ ] 建立固定问题、正确书籍、章节和正文块组成的测试集。
- [ ] 分别测量全文、向量和混合检索的 Recall@K、MRR/nDCG。
- [ ] 比较切块长度、重叠、模型、量化方式和 Top-K。
- [ ] 覆盖中文、日文、英文、跨语言、人名、虚构术语和短查询。
- [ ] 覆盖错字、近义表达、同义词和原句搜索。
- [ ] 测量单本/百本书建库时间、查询延迟、峰值内存和磁盘占用。
- [ ] 单独调查全文建库 1/2/4/6/8/12/16 并发的阶段耗时、CPU、峰值内存、磁盘和阅读延迟；用户初测 8 以上收益不明显。当前只采集证据，不优化流水线、不提高自动推荐值。
- [ ] 检索算法修改必须通过固定评测，不只依靠主观观察。

进入生成阶段前，智能检索和引用跳转必须已经稳定；生成模型不能掩盖召回错误。

## 第八阶段：生成式模型运行层

- [ ] Windows 默认采用项目构建、审计和固定版本的 llama.cpp sidecar，按需启动和停止；不要求安装 Ollama。
- [ ] GPU 是默认生成路径；CPU sidecar 是可选受限兼容组件，不承诺大模型速度，也不得在 GPU 失败后静默启用。
- [ ] 普通 UI 默认使用推荐 GGUF，只提供必要的启用、资源与加速模式；不建设面向普通用户的多模型市场。
- [ ] 高级用户可通过已校验 linked/约定目录替换兼容 GGUF，或启用 Ollama、局域网服务及远程 API Provider。
- [ ] 生成模型与嵌入模型分别配置和展示。
- [ ] 按设备内存、显存和模型大小给出提示。
- [ ] 模型按需加载，空闲后卸载；生成支持流式输出和取消。
- [ ] sidecar 使用临时端口/鉴权或其他受控 IPC，不暴露局域网。
- [ ] 子进程崩溃不能带走阅读器，应用退出必须回收进程。
- [ ] 更换生成模型不重建向量索引。
- [ ] 远程调用前明确展示发送范围和隐私影响。

## 第九阶段：带引用的 RAG 问答

- [ ] 支持当前章节、当前书、选定书籍和全书库四种范围。
- [ ] 使用混合检索召回原文，去除重复片段并控制上下文预算。
- [ ] 保留书籍和章节边界，避免跨书错误归因。
- [ ] 回答必须附带书名、章节、正文块和原文锚点引用。
- [ ] 点击引用回到原文，并明确区分模型回答与原文。
- [ ] 证据不足时允许拒答，不要求模型强行生成。
- [ ] 支持多轮追问，但限制会话上下文增长。
- [ ] 问答历史可保存、导出和删除。
- [ ] 无生成模型时降级为“问题 → 相关原文”，不伪装成完整回答。

## 第十阶段：AI 正文总结（最终目标）

总结必须分层完成，不能把整本书无条件一次性交给模型：

```text
正文块摘要
  → 章节摘要
  → 分卷摘要
  → 全书摘要
```

- [ ] 生成章节摘要并保存来源正文块。
- [ ] 支持无剧透简介和完整剧情总结两种模式。
- [ ] 生成人物、地点、组织、重要事件和时间线。
- [ ] 生成人物关系、主题、风格和内容警告建议。
- [ ] 开放式标签只能作为建议，并保留证据。
- [ ] 每一层摘要记录模型、提示词、算法和来源版本。
- [ ] 支持暂停、继续、取消、失败恢复和后台运行。
- [ ] 中间摘要可复用，修改最终提示词不必重算底层正文。
- [ ] 用户可以编辑摘要；用户版本与 AI 原始版本分开保存。
- [ ] 更换模型可以保留旧结果并比较，不静默覆盖。
- [ ] 阅读期间限制总结任务的CPU、内存和显存使用。

## 数据同步与隐私

- [ ] 阅读进度、书签等核心存档不依赖索引数据库。
- [ ] 正文副本、全文索引、向量和模型文件默认不进入同步存档。
- [ ] 用户标签、确认标签和用户编辑摘要可以同步。
- [ ] AI原始结果是否同步由用户决定。
- [ ] 删除书籍时清理其索引、问答和摘要派生数据。
- [ ] 提供清除全部 AI 数据和模型的入口。
- [ ] 本地推理不上传正文。
- [ ] 远程推理按当前章节/当前书/选定范围最小化发送内容。
- [ ] 模型文件、下载源和模型许可证分别审计。

## 性能和平台策略

Windows 基础全文搜索仍不要求独立显卡；语义建库与本地生成改为 GPU-first。无 GPU 的设备仍可使用全文搜索，只有用户显式启用受限 CPU 兼容模式时才进行本地模型计算。后台任务必须服从阅读优先级。Android 后续优先移植全文搜索和已生成分类结果，再评估量化嵌入模型；本地生成式模型不作为手机基础功能。

建议提供：

- 基础版：不含模型，全文搜索始终可用。
- 智能检索能力：默认推荐并管理一个经过验证的轻量嵌入模型；是否随包携带取决于许可证和安装体积，也可首次显式下载到用户选择的模型库。
- 生成能力：默认使用项目维护的 llama.cpp sidecar 与推荐 GGUF；运行组件可作为受控可选组件，模型不强制塞入主安装包。
- Ollama/远程 API：只作为高级兼容 Provider，不是任何基础发行形态的依赖。
- 所有模型：支持带 manifest/digest 的离线导入和重新定位；不支持绕过校验的任意文件替换。

## 推荐开发顺序

```text
1. 正文语料与稳定锚点（已完成）
2. SQLite FTS5、书架/阅读器共享搜索、Worker 建库与结果跳转（已完成，beta2 Windows 已验收）
3. 模型资产下载、离线 linked 导入、校验和管理（RAG C-57 代码完成，等待 Windows 发布版验收）
4. Core/AI发行门禁补强（C-57.6代码与本地矩阵完成；等待Windows双包验收）
5. 运行时准入与可恢复索引合同（C-58-Prep；只用mock）
6. Windows 硬件/后端探测、支持矩阵与资源准入（C-58A；不加载模型）
7. 单一通用GPU路径的Embedding Provider与可恢复语义索引（C-58B；不依赖Ollama；CUDA按性能证据后置）
8. 混合检索、相似内容和评测
9. 标签体系、建议标签和智能书架
10. GPU-first llama.cpp sidecar生成Provider；Ollama/HTTP高级兼容后置
11. 带引用的RAG问答
12. 章节摘要与全书分层总结
```

## 阶段目标与最终目标验收定义

阶段实现目标完成时，应满足：

> 用户无需生成式模型，即可对当前书和整个书库执行可靠的全文/语义混合搜索，查看相似段落和书籍，获得带证据的固定体系标签建议，并通过结果稳定跳回 EPUB 原文。

最终目标完成时，应满足：

> 用户可以选择内置、本地或第三方模型，在可靠检索基础上进行带原文引用的问答，并以可暂停、可恢复、可追溯的分层流程生成章节和全书总结；生成能力失效时，阅读、全文搜索和智能检索仍保持可用。
